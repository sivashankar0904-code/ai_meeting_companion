Audit Process Automation: project walkthrough

Short intro first, then the flow step by step. Draw the pipeline strip on the whiteboard, then walk the steps in order. Adjust every detail to what you actually built.

Short intro (30 seconds)

Audit Process Automation is a platform that helps an audit and compliance team deal with notices from authority portals. It pulls notices in, reads them with OCR, and uses AI agents to summarise each notice and draft the reply. People review and approve every reply, and only then does the system submit it back to the portal. I lead the team that built it. The frontend and backend run on EKS, the async work runs on Lambda, SQS and EventBridge, and the agents run on Amazon Bedrock AgentCore.

Architecture at a glance

Schedule 1: fetch notices, all clients→PDFs in S3 · Fetched→Schedule 2: OCR extraction→Fields in Aurora · Extracted→Schedule 3: AI analysis→Draft in UI · Draft ready→Reviewer / approver→Lambda submit→Portal

Purple runs on EKS, green is serverless or managed AWS, amber is a human step. Each schedule runs as a batch over every client and moves notices to the next status in Aurora. S3 holds the PDFs, and an append-only audit log records every step. Flowcharts 1 to 4 below draw each part.

Step by step
  1. Fetch the noticesEventBridge schedule 1A scheduled EventBridge run fetches new notices for all clients from the portals and downloads each notice PDF into S3. Every notice gets a row in Aurora with status Fetched. Each portal has its own queue, so one slow portal never blocks the others.
  2. Extract the filesEventBridge schedule 2, SQS, Lambda OCRThe next schedule queues one message per notice in status Fetched, carrying the notice ID and S3 key. A Lambda worker downloads the PDF from S3 and runs OCR on it: notice type, section, due date, amount. Digital PDFs give text directly, scans go through OCR. Long PDFs are split by page range to stay under the 15-minute limit. The text and fields go to Aurora, linked to the original PDF, and the status moves to Extracted.
  3. Track the statusBackend API on EKS, AuroraThe backend owns the notice status through a state machine, so each stage only picks up notices in the right status and a failed notice stays visible instead of being lost. It also serves the KPIs, caches in Redis, and pushes live status to the UI over WebSocket.
  4. AI analysisEventBridge schedule 3, SQS, Lambda, AgentCoreThe third schedule picks up every notice in status Extracted and queues one job per notice on SQS. A Lambda worker invokes AgentCore Runtime with a session ID. The worker supplies the tenant ID and notice ID, never the model. Slow LLM calls stay off the API pods.
  5. Draft the replySupervisor + 3 agentsA supervisor routes to the Summariser, then the Reply agent, then the Critic. The Critic runs deterministic checks first (section numbers, dates, amounts) and can send the draft back for revision, capped at 2 or 3 loops, then it escalates to a human. Agents use read-only MCP tools through AgentCore Gateway. They propose, they never act. The draft is saved and the status moves to Draft ready.
  6. Human approvalEKS backendThe preparer edits the draft and sends it to a reviewer, who approves or asks for changes. A high-risk or low-confidence notice also goes to an approver. Each decision updates the status. Roles are enforced on the server, and preparer, reviewer and approver must be different people.
  7. SubmitLambda, API → web → RPAA Lambda worker submits only when the status reads approved. It tries the portal API first, then web automation, then OCR-based RPA, and falls back only on technical failures. An idempotency key and the portal's acknowledgement number prevent double submission.
  8. Prove itAudit trail and monitoringEvery step is written to an append-only audit trail: who did what, the draft version, and the model and prompt version. A DLQ with alarms, plus AgentCore Observability traces, show failures. One query by notice ID rebuilds the whole story.
Three design points to land
  • Humans gate the flow, not the AI. Submission is irreversible, so nothing is filed without approval.
  • Right runtime for each job. EKS for always-on APIs, serverless for bursty and scheduled work, AgentCore for isolated agent sessions.
  • Reliability over scale. The load is low and spiky, so the queues, idempotency, retries and audit trail are there for correctness, not throughput.

Flowcharts

Draw these from memory on a whiteboard. Purple runs on EKS, teal is serverless or managed AWS, gray is data or a policy decision.

1. Overall architecture

  • EventBridge runs three schedules over all clients: fetch notices, then OCR extraction, then AI analysis. Each stage moves the notice to the next status in the database.
  • The Backend API on EKS owns workflow state and the approval state machine.
  • Lambda writes results and attempts, not status transitions.

2. AI analysis and drafting

  • EKS only queues the job. Slow LLM calls never block API pods.
  • Cap the Critic loop at 2 to 3 revisions, then escalate to a human.

3. Human approval and submission

  • Humans gate the flow, not the AI. Lambda submits only when the status reads approved.
  • Either gate can send the notice back to the preparer.

4. Agent layer: runtime, MCP tools and knowledge base

  • Each session runs in its own microVM, so one tenant’s session can’t see another’s.
  • Tools are MCP tools exposed through AgentCore Gateway. Agents propose, they never act: tools are read-only or validating.
  • Status changes, approvals and portal submission stay in the EKS backend and the worker Lambdas.
  • The notice text goes straight into the agent’s context. A knowledge base is optional and only for shared reference material.

What the load means for your answers
